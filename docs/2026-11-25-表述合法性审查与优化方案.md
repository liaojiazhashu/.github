## 3. 必须改（有实际法律风险或事实错误）

### M-1 ｜ 许可项目列出但未说明是否已取得
- **URL**：`/about.html`，主体信息表「许可项目」行
- **原文**：「网络文化经营、出版物批发、出版物零售、互联网信息服务（依法须经批准的项目，经相关部门批准后方可开展经营活动）」
- **问题**：这是营业执照「许可项目」栏的照录。该栏的含义是「取得许可证后方可经营」，不等于已取得。页面未做任何区分，读者（含潜在客户、监管、竞争对手）会读成「这家公司有这些资质」。
- **风险**：若实际未取得许可证而从事相应业务，属无证经营（《出版管理条例》《网络出版服务管理规定》《互联网信息服务管理办法》）；即便只是展示，也构成引人误解的表述。
- **建议改法**：在表下加一句限定，例如「上述许可项目须依法取得相应许可证后方可经营，本站不表示已取得相关许可」。或改为只列已取得的许可并注明证号。
- **⚠ 需用户确认**：这 4 项许可实际取得了哪些？（见 §6 事实边界 F-1）

### M-2 ｜ 「全站六个页面都没有输入框」与事实矛盾
- **URL**：`/contact.html` 隐私说明段
- **原文 A**：「全站六个页面都没有输入框：没有注册、没有订阅、没有留言表单。」
- **原文 B**（同页下一段）：「检索词就在那个地址里，会随访问日志一起被记录。」
- **问题**：三处矛盾。(1) A 与 B 自相矛盾——既然没有输入框，检索词从哪来；(2) `/library` 实测**有检索表单**（`/library/search?q=` 可正常返回 200）；(3) 图书馆属于「站」的一部分，全站说「六个页面」在结构上已过时（站点现在有 6 静态页 + 6 个图书馆页面）。
- **风险**：属《个人信息保护法》第 17 条告知义务的准确性问题——告知内容与实际不符，虽有 B 段补正，但 A 段的绝对否定表述会削弱整段告知的可信度。
- **建议改法**：A 改为「官网六个静态页面没有输入框：没有注册、没有订阅、没有留言表单。图书馆的检索框输入的词会出现在地址栏，随访问日志一起记录（见下）。」

### M-3 ｜ 「不接受任何闲杂分子」
- **URL**：`/community.html`，管理规则 01
- **原文**：「练笔群群内成员仅由练笔或评稿参与者组成，不接受任何闲杂分子。想先了解荒启科幻的人，可以加 QQ 群『荒启科幻交流群』进行交流。」
- **问题**：「闲杂分子」是带贬损意味的群体标签，把「非参与者」人格化贬低。同段后半句已经把正确做法说清楚了（引导去交流群），前半句是纯情绪表达。
- **风险**：不构成违法，但属不当表述；在公开页面出现这类措辞，对品牌（自称「纯公益社群」「连接创作者」）是自伤，也容易被截图传播。
- **建议改法**：删掉「不接受任何闲杂分子」，改为「练笔群只保留正在参与练笔或评稿的成员，不设旁观席位。」

### M-4 ｜ 词条页 AI 生成内容无标识
- **URL**：`/library/terms/<id>`（实测 `/library/terms/2417`）
- **问题**：词条页正文包含三段生成内容——释义（「在神经系统与外部设备之间建立直接信息通道的技术…」）、「01 · 起源与发展」、「02 · 世界科幻中的它」（三部代表作）——但页面**没有任何 AI 生成标识**。只有全站页脚一行「拆解由 DeepSeek 生成」，而词条不是「拆解」。
- **对照**：拆解卡页面做得很好（见 K-9），有独立区块标模型、提示词版本、生成时间、分析编号。词条页缺这一整块。
- **风险**：《人工智能生成合成内容标识办法》（2025-09-01 施行）第五条要求对生成合成内容添加显式标识，第六条要求元数据隐式标识。词条页正文属生成内容，无标识即不合规。
- **建议改法**：复用拆解卡的「这份拆解是怎么来的」组件，在词条页加「这份词条是怎么来的」区块（模型、版本、生成时间、编号），并在页脚披露句里把「拆解」改为「拆解与词条」。

### M-5 ｜ 「机器先写，人再校」与自动化上架流程矛盾
- **URL**：`/library/method` 与 `/library/works/<code>`
- **原文 A**（method）：「机器先写，人再校。出现在馆里的每一页，都是有人看过一遍的。」
- **原文 B**（拆解卡「这份拆解是怎么来的」）：「本拆解由 DeepSeek 生成，编辑于 2026-11-20（**一键拆解自动上架**）。编辑后的结论与模型原始输出不完全一致。」
- **问题**：A 声称每一页都经过人工审校；B 的括注「一键拆解自动上架」指向自动化流程。两者若同时成立，需要说明「一键上架」环节里哪一步是人做的；若不成立，A 就是不实陈述。
- **风险**：这是本次审查里**唯一一条可能构成虚假宣传**的表述——它直接关系到服务质量承诺，且写在方法论页面（读者据此建立信任）。同时它也是 AI 标识合规的关键事实：办法要求标识「生成合成内容」，而人工实质编辑后是否仍算生成内容、如何标注，取决于真实流程。
- **建议改法**：先确认事实（见 F-2），再统一口径。两种走法：
  - 若确有逐篇人工复核：拆解卡的括注改为「一键生成 + 人工复核后上架」，并在此处记录复核人角色（不需实名）。
  - 若复核仅为抽检或格式化：method 页改为「机器先写，编辑再校。出现在馆里的每一页都经过编辑处理，其中抽检比例与复核方式见下」，并给出真实比例。

### M-6 ｜ iOS 客户端格式标注错误
- **URL**：`/`（客户端下载区块）、`/contact.html`（#start 区块）
- **原文**：链接文字写 `.ipa`，`href` 实为 `huangqisf.mobileconfig`；contact 页正文亦写「iOS 端（.ipa）三个版本」。
- **问题**：`.ipa` 是 iOS 应用安装包，`.mobileconfig` 是配置描述文件（此处显然用于引导安装或描述文件分发）。两者不是同一类文件，写错会让用户按 .ipa 的预期去操作。
- **风险**：事实错误，不涉法律定性，但属「对商品的性能、功能作虚假或引人误解的宣传」的边角（《广告法》第 28 条），且直接影响可用性。
- **建议改法**：三个页面（含 `.build/pages/*.html` 源）统一改为「iOS 端（描述文件）」或「iOS 端（通过描述文件安装）」。**注意三个 `/dt/` 文件当前全部 404**（挂起中），修文案前需一并决定下载链路去留。

## 8. 全面优化方案（五块）

### 一、部署与稳定性

**现状**
- `git pull --ff-only` 每 5 分钟一次（cron），部署脚本 `/www/wwwroot/deploy-zha.sh`，日志 `/var/log/zha-deploy.log`
- `server/bin/check-boot.php` 409 行，8 项断言，覆盖：装配期不连库（A）、`/healthz` 降级（B）、`/`、`/library/`、`/library`、`search 500`、`work 404`、`admin/login 500`（C），另查 7 个安全头与 6 类信息泄露
- 近 3 个月两次真实故障：11-03 数据库挂掉时全站 500 且 0 字节白屏；11-25 `/library/` 因 `static fn` 静默 500

**问题**
1. `check-boot.php` 是**本地回归**（把 DB 指到 `127.0.0.1:1` 模拟故障），不是线上存活探测——它证明「代码在降级场景下不崩」，不证明「线上现在是活的」
2. cron 每 5 分钟 pull，但没有「pull 失败重试/告警」这一层，失败只落日志
3. `check-boot.php:405-407` 自己记了一条已知缺口：错误响应不带安全头（错误中间件在最外层，内层 `SecurityHeadersMiddleware` 补不上）
4. 11-25 那次 500 潜伏了很久，原因写在注释里：「之前自检只测了 `/` 和 `/library`」——覆盖面靠事后补，没有「新增路由必须进自检」的约束

**改法**
1. 把 `check-boot.php` 加入部署脚本后置钩子（pull 后跑一次，退出码非 0 则写一条醒目的失败记录），成本约 20 行 bash
2. 给 `check-boot.php` 加一条「路由表全量冒烟」：遍历 `routes.php` 里所有 GET 路由，用真实容器 dispatch 一遍，断言「不 500、不白屏」。这一条能自动抓住 11-25 那类问题
3. 修已知缺口：给 `LibraryErrorPage` 的样式改外链，然后打开「错误响应必须带安全头」的判红条件

**工作量**：1 项约 0.5 天；2 项约 1 天；3 项约 1.5 天（要动错误页模板 + CSP）

### 二、SEO 与可达性

**现状**
- `/sitemap.xml` 200，1,088 条；`/robots.txt` 200，已声明 sitemap 并 Disallow `/admin/`、`/server/`
- `/library` 有 canonical + og:url；静态页（含 `/library.html`）无 canonical
- 已定：保留静态 `library.html`，不删不 301，维持「介绍页 + 应用」分工
- `search` 页 `noindex, follow`，`admin` 页 `noindex, nofollow`

**问题**
1. 静态六页**无 canonical**，而 `www.huangqisf.com` 与本站同品牌同内容嫌疑（F-4），重复内容风险未处理
2. sitemap 1,088 条 vs 馆藏实际 718 篇拆解 + 174 词条 = 892，差额需核对（可能 sitemap 含期次/作者页）
3. `/library.html` 不在 sitemap（结论：可接受，它是介绍页，删了也无收录损失；但若保留应在页内自链 `/library` 明确主入口）
4. 静态页 title 用全角竖线「｜」，动态页用「 · 」+ 半角竖线，品牌分隔符不统一

**改法**
1. 静态六页在 `.build/pages/*.html` 加 `<link rel="canonical">`（走构建脚本注入，避免手工改 6 份）
2. `www.huangqisf.com` 与本站的关系确认后（F-4），决定 canonical 指向或 robots 互斥
3. 统一 title 分隔符为「 · 」（与动态页一致）

**工作量**：约 1 天（含构建脚本改 + 重跑 + 六页复测）

### 三、性能（UTF-8 字节数）

**现状（实测）**

| 资源 | 字节 | Cache-Control |
|---|---|---|
| `index.html` | 55,362 | **无** |
| `css/style.css` | 97,390（线上） | `max-age=604800` |
| `js/main.js` | 24,279 | — |
| `noto-sans-sc-400.woff2` | 252,864 | `max-age=604800` |
| `noto-sans-sc-700.woff2` | 255,792 | `max-age=604800` |
| `inter-latin-400.woff2` | 23,692 | — |
| `logo-full-dark.png` | 74,939 | `max-age=604800` |
| `/library` | 38,423 | `public, max-age=60` |

字体目录合计 897,376 B（11 个文件），`assets/logo` 153,045 B，`assets/qq` 33,616 B。

**问题**
1. **首屏字体是最大单项**：首页引 2 个 Noto Sans SC（508,656 B）+ Inter（23,692 B）= 532 KB，超过 HTML 本身的 9.6 倍。已有 `tools/subset-fonts.py` 却显然未对全站字形做子集化（250 KB 级说明是全量字形）
2. `index.html` 无 `Cache-Control`（nginx 默认对 HTML 不发），可接受但应显式给 `no-cache` 或短 TTL，避免中间层缓存旧页面
3. `logo-full-dark.png` 74,939 B 是 PNG，可转 WebP/AVIF 或 SVG（logo 是几何图形，SVG 最优）
4. `/library` 只给 60 秒缓存，而它的内容按「每月 16 日 18:00 重算」更新，60 秒过于保守

**改法**
1. 跑 `python tools/subset-fonts.py` 对全站扫描字形并重建子集（这是既有工具，缺的是没跑），预期 Noto Sans SC 从 252 KB 降到 30–60 KB 级
2. `logo-full-*.png` 改 SVG（矢量，几 KB）；至少转 WebP
3. `/library` 的 `max-age` 提到 300（数据变化频率远低于此）
4. HTML 显式加 `Cache-Control: no-cache`

**工作量**：1 项 0.5 天（跑脚本 + 复测字形无缺）；2 项 0.5 天；3–4 项 0.5 天（nginx 层）

### 四、可维护性

**现状**
- `.build/pages/*.html` → `node tools/build-pages.cjs` → 根 `*.html`；`.build/css-parts/*.css` → `node tools/build-css.cjs` → `css/style.css`
- `tools/check-site.cjs` 存在但 `:36-38` 与 `:217` 直接跳过站内绝对路径校验（所以 `/dt/` 三个 404 从未被发现）
- 新增汉字必须跑 `python tools/subset-fonts.py` + `python tools/check-fonts.py`，否则静默回退系统字体

**问题**
1. **构建后需要手动做三件事**（build-pages、build-css、subset-fonts），漏做任何一件都无报错——字形缺失是静默的，这正是最危险的一类
2. `check-site.cjs` 跳过根绝对路径，站内 404 检测形同虚设
3. 硬编码路径：`build-pages.cjs:117-122` 的 `APP_DOWNLOAD` 常量与 `:84` 的 `LIBRARY_URL` 都写死了 URL，页面里散落 23 处 `href="library.html"`
4. 两个构建脚本各自独立，没有统一的 `npm run build`

**改法**
1. 加一个 `tools/build-all.cjs`：串行跑 build-pages → build-css → subset-fonts → check-fonts → check-site，任一步失败即中止。`package.json` 加 `"build": "node tools/build-all.cjs"`。**这是收益最高的一条**，把「四步手工」压成一条命令
2. 修 `check-site.cjs` 的根绝对路径校验：`isRootAbsolute()` 命中后仍应做存在性检查（本地 `fs.existsSync` + 已知的「不进 git 的部署附件」白名单 `/dt/`）
3. 把 `APP_DOWNLOAD` 与 23 处 `library.html` 收敛到构建脚本常量

**工作量**：1 项 0.5 天；2 项 0.5 天；3 项 1 天（改动面大，需逐页复测）

### 五、可观测

**现状**
- `/healthz` 200，返回五项检查全 ok：db、storage、ai、queue、runtime
- `/var/log/zha-deploy.log` 记录部署结果
- 无任何外部探针、无告警、无 uptime 监控

**问题**
1. **有能力，没人用**：`/healthz` 已经是活的且信息完整，但没有定时任务打它，也没有失败告警
2. 11-25 那次 `/library/` 500 是靠人工发现（主 Bot 报告）的，不是系统发现
3. 部署失败只写日志，没有人读

**改法**
1. 加一条 cron：每 5 分钟 `curl -fsS https://zha.ruletree.club/healthz`，非 200 或 JSON 里任一 check 非 ok 就发邮件/推送（复用现有通知渠道）
2. 部署脚本失败时同样告警
3. 可选：把 `/healthz` 的检查项扩到包含「`/library/` 是否稳定 302」（就是这次 500 的那条）

**工作量**：1 项 0.5 天（需要用户提供通知渠道，如邮件地址或 webhook）；2 项 0.5 天；3 项 0.5 天

**五块合计**：约 8–9 个工作日的改动量，其中「构建一条命令」与「健康检查探针」两条收益最高、成本最低，建议先做。
