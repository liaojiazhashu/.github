数字化产品开发

我们先做一个自己愿意长期使用的产品，再把它做成可以对外提供的服务。 投稿、分配、评分与汇总的流程，靠聊天窗口和在线表格撑不了几期 —— 于是成都荒启文化传播有限公司写了一套系统，一路用到今天。 现在这套能力向外开放：社区与内容系统、教育考试系统、AI 应用、定制开发， 从一个模块到整套产品，都可以交付。

本页所述系统开发与技术服务由成都荒启文化传播有限公司提供，以公司全称签约。 「荒启科幻练笔」由科幻爱好者自主运营、独立开展活动，为纯公益社群，参加活动不向参与者收取费用。

起点

一套系统真正的成本，不在开发，在「说不清楚」

把一件事搬到线上，要过三关：把流程说清楚、把系统建起来、把系统养下去。 多数团队卡在第一关 —— 不是不懂业务，而是业务平时存在于人的习惯里， 一旦要写成规则，才发现同一个环节三个人有三种做法。

所以开发从真实使用开始。练笔活动每年九期，每期都有收稿、分配、评分、 汇总、公布、结算，跑满一期就能暴露一批没想清楚的地方。这套系统就是这样长出来的： 需求不是写在文档里的假设，而是「这一期又卡在哪」的具体记录。

一般做法的三个坑

  • 先做功能清单，再回头补流程，最后发现流程本身要改
  • 系统上线即交付，运营改一个字段都要排期
  • 数据只能进不能出，换一家供应商等于从零开始

我们的做法

  • 先画流程再定功能，流程确认后功能清单才有意义
  • 配置项全部开放给运营，改维度、改文案不用等版本
  • 数据与源码可交付，任何时候都能整体搬走

拆开看

四条业务线，其实都由这五层组成

下面按「层」而不是按「产品」来讲。每一层先说明通用能力， 再指出换到社区、教育或 AI 场景时它变成什么 —— 这样可以按层选， 也可以整套上。可按功能点勾选，不必为一行用不上的代码付费。

先定谁是谁，再谈功能

任何一套系统，第一个要落地的都不是功能，而是身份：谁能看、谁能写、谁能批。 不同业务线的角色模型差别很大 —— 社区是会员与版主，教育是教师与班级， AI 应用是调用方与知识库范围 —— 但都能归到「角色 × 资源 × 动作」这一张表上。

  • 多角色与自定义权限组：内置管理员 / 编辑 / 审核 / 普通用户，可自由组合
  • 会员体系：等级、成长值、勋章、订阅，名称与层级可按行业习惯重命名
  • 组织关系：班级、院系、门店、项目组等树形归属，支持一人多归属
  • 登录方式：手机号验证码、微信、企业微信、学校统一身份认证
  • 数据可见范围：按角色、按归属、按字段三级控制，默认最小可见
  • 操作审计：谁在什么时候改了什么，全量留痕且可导出

内容不是文件，是带状态的数据

把稿子存下来只解决一半问题，另一半是「这篇现在处于什么状态、谁能看到哪一版」。 版本、编号、可见性与状态机绑定之后，投稿的多轮稿、课程的章节改版、 知识库的文档迭代，可以共用同一套模型。

  • 版本留痕：任何内容可回溯、可对比，历史版本不被覆盖
  • 唯一编号与匿名：进入评审或盲评阶段后以编号代替署名
  • 状态机：草稿 → 待审 → 发布 → 归档，状态与流转权限均可自定义
  • 多形态内容：图文、视频、附件、结构化题目、文档切片，统一检索
  • 提交校验：字数、格式、必填项即时校验，避免后期返工
  • 全量导出：结构化格式随时带走，不设离场障碍

把「谁该做什么」从人脑搬进系统

流程最容易出错的环节是分配：分给谁、凭什么分、分错了怎么改。 评稿分配、组卷阅卷、工单派发，本质是同一件事 —— 按规则把任务派给合适的人，再把结果收回来算。

  • 任务分配：算法 / 随机 / 人工指定 / 交叉分配，规则可配、过程可追溯
  • 评分与评价：多维打分 + 文字评价，维度权重可设，超过阈值自动去极值
  • 自动化：随机组卷、客观题自动判分、工单派发与超时升级
  • 催办提醒：站内、邮件、短信、公众号、群机器人多通道，按时段限流
  • 复核申诉：对单条结果可提复议，完整沟通记录留档
  • 结果产出：个人反馈单、期次汇总、可对外出具的正式报告

一套代码，每个终端各有各的脾气

六端不是把同一个页面复制六遍。Web 要能被搜索引擎收录，小程序要过审核且有体积限制， APP 要能推送与离线，H5 要能在别人的浏览器里跑。共用业务代码与设计系统、 差异部分按端单独封装，是我们认定的唯一合理做法。

  • Web 网站：服务端渲染或静态生成，首屏快、可被收录，适合官网与内容站
  • 微信 / 抖音小程序：一套代码分别编译，按平台规范适配登录、分享与支付
  • 安卓 / iOS：同一套业务代码编译原生应用，支持推送、扫码与离线缓存
  • H5：可嵌在公众号、群聊或第三方 App 内，打开即用，不必安装
  • 设计系统：颜色、间距、字阶一套令牌贯通六端，改一处全端生效
  • 管理后台：与前台共用权限体系，桌面优先，移动端可应急处理
代码复用业务逻辑与组件共享，端差异单独封装

服务端Spring Boot 3.5+ / JDK 17+，按业务域拆服务

后台不是给程序员看的，是给运营看的

一套系统能不能长期活下去，取决于运营能不能自己改配置：改评分维度、发通知、 导报表、查日志。后台的第一用户是运营，不是开发者。集成层则负责把系统接回 已有的生态 —— 公众号、群、表格、内部系统。

  • 运营后台：内容审核、用户管理、配置项、活动开关，全部可视化
  • 数据看板：活跃、转化、完成率、留存，可按时间与分组筛选
  • 报表：导出 XLSX / CSV / PDF，按期自动推送到群或邮箱
  • 开放接口：REST + Token 签名，按应用授权范围，附调用示例
  • Webhook 与群机器人：事件触发外部系统，失败重试且可查投递日志
  • 第三方对接：微信生态、在线支付、短信、对象存储、组织现有系统

结构对照

每条业务线，骨架其实是同一个

把每条业务线剥到只剩骨架，都是三段：对象 → 处理 → 结果。 中间那一步决定这套系统好不好用，也决定了要花多少钱 —— 先确认对象是什么，后面几层自然成立，选型就不会被功能清单牵着走。

稳定性怎么保证

  • 业务都有「集中那一刻」：截稿前 24 小时、考试开考、活动开场。这些时间窗单独压测
  • 内容与结果自动落库并每小时快照，误删可回滚到上一个快照
  • 接口带幂等键，网络抖动导致的重复提交不会变成两条记录
  • 升级先上灰度环境，跑满一个完整业务周期才推到正式环境

合作方式

三种合作方式，功能完全一致

三类客户的技术人力差别很大，所以三种方式都按「交付之后没有专职技术人员也能长期运行」设计。 区别只在数据放在哪、能改多深、以后谁维护 —— 多数组织从托管版起步， 规模稳定后再迁移或买断。

咨询源码买断
源码与文档一并交付

不管选哪种方式，交付物里都包含数据库结构与接口说明。托管版可按需导出， 私有化与买断版直接给源码 —— 不存在「系统是你的，但代码不是」。

双周迭代

需求进排期后按两周一个版本推进，每个版本结束可演示；验收不过的改动不进入下一版本， 避免问题越滚越大。

上线之后仍有人管

上线首月由公司提供运维保障，之后按年提供缺陷修复、性能优化与版本升级， 服务范围与响应时限以技术服务协议约定为准。不追求「验收即失联」的一次性项目。

报价按模块算

按功能模块、复杂度与交付周期报价，签约前给出明细；后续没有追加的隐藏项， 需求变更单独评估、单独确认。

交付流程

五步走完，先跑通再扩展

我们从不建议一次性把所有功能都打开。真实需求往往要在一次完整业务周期之后 才会显形 —— 先跑通最小闭环，再根据实际使用情况扩展，是成本最低的路径。 定制项目在此基础上多一道原型与方案确认，避免做到一半才发现方向不对。

流程梳理

把你的业务从头走一遍：一次活动怎么开、材料怎么收、任务怎么分、结果怎么公布。 我们把它画成流程图，逐环节确认哪些需要系统承接、哪些可以直接简化。

原型与方案

给出关键界面的可点击原型与功能清单：哪些是标准能力、哪些需要定制、 分别影响多少工期。这一步确认之后才进入开发，避免边做边改。

开发与试运行

双周一个版本，每个版本结束可演示。开发完成后用一批历史数据做完整试运行， 验证流程是否走得通、数据是否对得上、权限是否有漏洞。

正式上线

导入正式数据，开放入口。上线首月我们全程陪跑，处理突发问题并同步记录改进项， 一个完整周期结束后给出问题清单与优化建议。

迭代扩展

基于实际使用数据决定下一步：补模块、调规则、加对接。 每次迭代都以「能减少一项人工操作」为标准，不做没有使用场景的功能。
